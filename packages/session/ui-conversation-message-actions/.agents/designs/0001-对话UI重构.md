# 对话 UI 重构：引用解析、数据保真与渲染分层

决策前提见 [ADR 0006](../adrs/0006-复制上游对话UI的client半并禁用官方行.md)（按上游包边界复制
`ui-conversation` / `ui-chat` / `ui-input-trigger` 三个 client 包并禁用官方行）与
[ADR 0007](../adrs/0007-引用的统一解析与渲染转换.md)（引用**解析与渲染分离**：解析产出统一结构的引用，
渲染时转换到官方 markdown 渲染器的 chip 钩子）。接管本身登记在
[债务 0001](../../../../../.agents/debts/0001-临时接管上游对话UI的client半.md)（`临时接管上游对话 UI 的 client 半`）。

## 一、问题

四项诉求对应的现状缺口（取证见 ADR 0006）。ADR 0007 之后，缺口只剩三处：

| 诉求              | 现状                                                                                             | 处置                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| 引用无法表达      | 官方 `ContentBlockMap` 无资源块；`file` 块只有 sha256 附件引用；ACP `resource_link` 入站即文本化 | 引用走 text 块里的文本形态，统一解析（第二节），不新增块类型 |
| 用户输入被预处理  | composer 无 ContentBlock 模型：引用只是文本，没有能携带行号范围的形态                            | 「文本即真相」：引用就是文本（第三节）                       |
| 正文进消息文本    | 把文件内容 / skill 正文内联进消息与官方「选中不读内容」的取向相反，也重复付费                    | 后注入（第四节）                                             |
| 思考块无 Markdown | `ReasoningRow` 直出纯文本，摘要手工 `replaceAll('**','')`                                        | 未做（第六节）                                               |

一个支撑事实：**host 侧的队列与落库本身没有丢失结构**——排队输入就是同一个 `UserMessage`（同 id、同
`ContentBlock[]`），step 边界 claim 时同一条消息被 append 成 `user/message`
（`.../core/agent-loop/src/inbox.ts:230-245`）。丢结构的一直是 client 的输入表示与渲染投影。

## 二、引用：统一解析（解析与渲染分离）

所有书写形态都用 markdown 解析器（`mdast-util-from-markdown` + GFM + 我们的 micromark/mdast 扩展）归一
到同一个结构——**host 与 client 共用同一份 `findReferences`**：

| 书写                                | 归一                                                             |
| ----------------------------------- | ---------------------------------------------------------------- |
| `skill:xxx` / `@skill:xxx`          | `{ protocol: 'skill', path: 'xxx' }`                             |
| `@xxx`（手打的裸路径）              | `{ protocol: 'file', path: 'xxx' }`                              |
| `@xxx#L12-L40`                      | 同上 + `lineStart: 12, lineEnd: 40`                              |
| `@xxx:1:2`                          | `{ protocol: 'file', path: 'xxx', lineStart: 1, column: 2 }`     |
| `[label](src/a.ts)`                 | `{ protocol: 'file'（默认）, path: 'src/a.ts', title: 'label' }` |
| `[label](src/a.ts#L12-L40)`         | 同上 + `lineStart: 12, lineEnd: 40`                              |
| `[label](https://example.com/a.ts)` | `{ protocol: 'https', origin: 'example.com', path: '/a.ts' }`    |
| `@[label](dsh-session:…)`           | `{ protocol: 'dsh-session', path: '…', title: 'label' }`         |

```ts
export interface Reference {
  readonly protocol: string; // 默认 "file"
  readonly origin?: string;
  readonly path?: string;
  readonly title?: string;
  readonly lineStart?: number;
  readonly lineEnd?: number;
  readonly column?: number;
}
```

- `protocol` **默认 `file`**：无 scheme 的相对路径 link 也是 file 引用；http(s) 走同一套（`origin` + `path`）；
- 裸形态由 micromark 扩展认领（词边界起手；`@` 起手的路径无行号也认领、`#L12-L40` fragment 一并吃掉——本 UI
  没有 cue 人，`@handle` 一律当路径；非 `@` 的裸形态必须已知 scheme，`x:y` 不会被吃掉）；
- link / mention 形态由 mdast 转换层认领（label → `title`；`@` 紧邻时并入 span）；
- 代码块与 inline code 内的同形文本由解析器天然排除——**不做文本层全局正则替换**；
- 生成侧（pick / 粘贴）写裸 URI：`formatReference` → `file:src/a.ts#L12-L40` / `skill:code-review`
  （目录写成 `file:src/session/`）；行号 / 列号的生成形态是 `#L12`、`#L12-L40`、`#L1C2`。

## 三、输入、提交与回填

- **插入**（菜单 pick）：conversation 输入汇把引用源给出的插入形态归一到裸 URI 文本
  （`reference-text.ts` 的 `referenceTextOf` / `insertTextOf`），facade 的 `insertReference` 把它当
  **普通文本**替换 pick span（尾随空格规则沿用）——**不创建 chip 节点**，草稿里没有结构化引用状态；
- **粘贴**：剪贴板 meta 带路径时落裸 URI（行号范围进 fragment），工作区内的绝对路径落成相对路径
  （`clipboard-resource.ts` 的 `clipboardUriOf` + `pasteTextOf`）；读不到路径时保持纯文本粘贴；
- **提交**：草稿原文即模型文本的一个 text 块（`sinkSerialized` 回到上游实现：有 chip 时按 codec splice），
  不再切块；
- **回填**（编辑 / 撤回）：消息各 text 块按空行拼成 raw markdown 落回输入框（`restoreDraft(draft)`）；
- **输入框不做引用渲染**：编辑器里显示原文，不建 chip 节点、不装饰；
- **命令路径不变**：`/command` 仍走 `remote.commands.execute`，不产生 `user/message`。

## 四、后注入（host）

引用正文由 host 的 `agent/pre-step` 边界注入，形态与官方 `/name` 手势一致：

- `protocol === 'skill'` 的引用 → `@morlay/dsh-reference-injection` 用 `ctx.skills.get` 取定义并渲染
  `<skill_content>`，作为 instructions 形态的 user 消息追加在本步已有注入之后
  （`source.kind = 'skill-invocation'`）；判定与官方手势一致（未知 / 不可调用 → 保持普通文本）；
- 解析复用 client 面同一个 `findReferences`（手写的 `` `skill:x` `` 由 `parseReferenceToken` 再兜一次）；
- **未做**：文件引用的正文注入——模型现在对文件引用需要自己 `read`。

## 五、渲染

一个渲染入口，三处复用（消息气泡、队列行、pending steering 与提交 echo）：`ReferenceMarkdown`
（= 统一解析 → 本地引用切片转 token → 官方 `MarkdownText` + `fileMentions` → chip）。

- **不 fork 渲染器**：官方包公共面只有 `MarkdownText` / `CodeBlock` / `extractMarkdownPlainText`，
  `renderBlocks` 不在公共面，且官方包在 client 侧是平台 baseline external（模块表按精确包名注册，
  子路径 require 必 miss）；官方唯一的 chip 钩子是 `fileMentions`（只认 inline code），所以转换规则是：
  本地引用（非 http / https / mailto）的原文切片换成 token，http(s) 等外部地址保持 link 原文；
- chip **显示文本省略 protocol**（图标已表示协议）：有 label 就用 label（`[实现](src/a.ts#L12-L40)` →
  `实现`），否则用 path + 行号范围（`file:mise.toml` → `mise.toml`、`skill:code-review` → `code-review`）；
  hover 与 aria-label 是完整引用；图标由官方 `LinkIcon` / `classifyLinkPath(显示文本)` 决定；
- 判定不靠文本形态：转换同时产出「显示文本 → Reference」映射给 `fileMentions.resolve`，所以没有路径特征的
  skill 名也能成 chip，普通 inline code 不会误判；
- 点击 file → `openFile`、skill → `openSkill`（owner props，打开右侧栏）——**keyed 渲染器也要从 owner props
  取这两个动作并透传**，否则点击无反应；没有 `actions` 时照常渲染但点击无效果；
- 三处消费点：`ui-chat/src/client/chat/MessageItem.tsx`（user / steering 气泡，含 pending 与提交 echo）、
  `ui-conversation-message-actions/src/client/chat-node/MessageItem.tsx`（keyed shadow，实际生效的那份）、
  `ui-conversation/src/client/queue/QueueDock.tsx`（队列行与本地 echo，无 actions）；
- `MarkdownLabels` 适配（`markdown-labels.ts`）在 `@morlay/dsh-client-ui-primitives` 里一份，三个消费方共用。

## 六、思考块 Markdown（未做）

计划：我们自己的 `ReasoningRow` 正文走 markdown 渲染，折叠摘要改用 `extractMarkdownPlainText`
（官方现成导出），不再用 `replaceAll('**','')` 手撕标记。

## 七、队列（未做）

计划：替换 `QueueDock`——去掉 inline edit，编辑 / 撤回统一走「撤回 inbox 修改」；渲染入口已与气泡共用。

## 八、接管与禁用清单

- **禁用**：`ui-conversation`、`ui-chat`、`ui-input-trigger` 三行，一对一替换为
  `@morlay/dsh-client-ui-conversation` / `-ui-chat` / `-ui-input-trigger`。
- **保留**（靠同形声明继续工作）：`ui-attachment`、`ui-reference`、`ui-skill`、`ui-commands`、
  `ui-model-selection`、`ui-approval`、`ui-tool`、`ui-cordis`、`ui-trajectory`、`ui-sidebar-*`、`ui-settings-*`。
- **官方的 `ui-primitives` 仍是平台 baseline**（前端种子提供，不可替换）：markdown 渲染与 chip 外观都来自它。
  我们自己的 `@morlay/dsh-client-ui-primitives` 是另一个包（css-in-js kit + 引用解析 + 渲染转换 +
  `MarkdownLabels` 适配），三个 fork 的 client 包都依赖它。
- **同形声明**：ui-conversation 的 22 个槽 + ui-chat 的 6 个槽与上游逐字一致；`ui-input-trigger` 的
  `InputTriggerSource` / `InputTriggerServiceContract` 只在 `appearance` 词表上扩展。
- **host 侧新增**：`@morlay/dsh-reference-injection`（skill 后注入），装配在
  `packages/preset/dsh-preset/cordis.patch.yml`。

## 十、验证策略

- **单元**：统一解析（各书写形态、行号 / 列号、label、`dsh-session:` 原样、http(s)、代码块与 inline code 排除、
  多个引用顺序）、生成侧（`formatReference` / 插入形态归一 / 粘贴分类与工作区相对化）、host 的 `skillNamesIn`；
- **组件**：jsdom 断言 chip（`file:mise.toml`、`skill:xxx` 成 chip；点击调 `openFile` / `openSkill`；
  `[label](https://…)` 仍是锚点；普通文本与普通 inline code 不受影响）；
- **回归**：历史纯文本会话的 `@path` 认领成 file chip、`/name` 按普通 markdown 渲染不报错；
- **集成**：composer → 提交 → 会话日志单 text 块断言 → 渲染断言。

## 十一、未决问题

1. 文件引用的后注入边界：只有「带行号范围」注入正文，还是裸路径也注入（当前取向：只 range）；
2. 其它 protocol（`dsh-session` 等）的 chip 显示文本与点击目标（当前显示 path、无点击目标）；
3. 目录 token（`file:src/dir/`）的 folder 图标：官方 `classifyLinkPath` 按扩展名判定，当前是通用纸张图标；
4. 其它 protocol（`dsh-session` 等）渲染成 chip 但暂无点击目标（会话预览）；
5. 手打 `/name`（官方 skill 手势）在 markdown 渲染下的 chip 外观；
6. 队列去 inline edit 的迁移时机（涉及 `QueueDock` 与撤回路径的交互）；
7. 编辑器内的 chip 节点机制（`chip-node.tsx` / `ReferenceChip.tsx` / `projection.ts` 的 chip 分支 /
   `Occurrence` 契约）在 pick 改落文本后已无产生点，是否连同 `slash/input-insert-reference` 的 chip 语义一起清理。
