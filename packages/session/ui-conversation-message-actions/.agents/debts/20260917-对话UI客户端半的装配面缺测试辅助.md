# 对话 UI 客户端半的装配面缺测试辅助

状态：未销账（对话 UI 接管面与编排层的 slot 装配面无测试，缺 client 侧 harness）

**现象**

对话 UI 接管面（`session/ui-conversation`）与编排层
（`session/ui-conversation-message-actions`）的**行为逻辑**已按接缝测（接缝清单见
[本包规范 how-to-verify](../standards/how-to-verify.md) 与 [接管包的 how-to-verify](../../../ui-conversation/.agents/standards/how-to-verify.md)），
但 **slot 装配面**仍无测试：

- `session/ui-conversation`：`client/apply.ts`（插件装配 + slots 注册）、`client/skeleton/*.tsx`
  （`ConversationRoot` / `ConversationSession` / `InputBar` / `ContextMeter` / `TodoPanel` 等）、
  `client/service.ts`（`ConversationController`：附件上传队列 / `sendSession` / queue 操作）；
- `session/ui-conversation-message-actions`：`client/index.ts` 的 `apply`
  （slot 注册 + `conversation.session.header.utilities` 注入）。

例外（已覆盖的装配面）：`conversation.composer.dock` 的 `stats` 覆盖注册
（`client/composer-stats/register.ts`）由 `composer-stats.spec.ts` 直接驱动真实的
`SlotCore`（`@deepseek-ai/dsh-client-ui-slots`，纯注册表，不需要浏览器运行时）——
声明槽、注册官方同 id 行、再跑我们的注册，断言赢家 id / priority / locale / 组件。
同一手法可用于 `user` / `steering` 的 keyed 覆盖。

**影响**

这些模块需要 **cordis client 运行时**：`slots` 的声明者与注册表、`locale`、`renderer`、`sessions`
面（binding / scope），以及浏览器模块图。当前仓库没有 client 侧 harness；vitest 的
`@morlay/*/client` alias 只把本仓库包的 `/client` 回源到 TS 源码，而**上游 client 半是浏览器模块
工厂**（`window.__ModuleLoader__.load`），node 侧不可加载——所以无法在 node/jsdom 里装配真实的
slot 运行时，强行逐份 stub 只能得到「实现镜像」式的断言，不能验证装配契约。

**触发条件**

动到这些 `apply` / 装配面之前——没有测试就改装配，slot key / priority / locale 与注入面的回归只能
靠人工跑 GUI 发现。眼下卡在「没有 client harness」，见销账条件的两个选项。

**销账条件**

Done when：装配面有真实用例守护，满足任一项实现路径即可结算本记录：

1. 上游提供可用的 client 测试运行时（例如 `@deepseek-ai/dsh-client-test-runtime` 的
   `SlotTestRuntime` 一类能力），可在 node/jsdom 中注册 slots / locale / renderer 与 sessions 面；
2. 我们自己建一个 client harness（最小 slots 声明者 + 注册表 + locale + sessions binding stub），
   必要时把 vitest alias 扩展到所需的上游 client 子路径（types → src）。

具体落地动作：

- 建 harness（放共享 devpackage 或 `packages/client/*/src/testing.ts`）；
- 给上面列出的 apply / 组件装配面补 jsdom 用例：断言 slot 注册的 key / priority / locale、
  注入面方法可用、渲染出用户可见结构；
- 结算本记录，并同步更新两个包 `.agents/standards/how-to-verify.md` 的未覆盖清单。

**不修的理由**

补的不是断言而是整套运行时：在 harness 出现前写不出有验证力的用例（只能镜像实现）。已覆盖的部分
（核心纯逻辑与用户可见组件的接缝测试）是有效的，装配面的空白可以等 harness。

## 基线

- fork / 接管基线：`DEEPSEEK_HARNESS_VERSION`（见根 `mise.toml`）；
- 差异登记见[债务 临时接管上游对话UI的client半](../../../ui-conversation/.agents/debts/20260917-临时接管上游对话UI的client半.md)；
- 已覆盖部分（不在此结算）：核心纯逻辑（事件→视图投影、消息定位、输入 / 队列状态机、引用检测与
  菜单）与用户可见组件（气泡、队列行、引用菜单）的接缝测试。
