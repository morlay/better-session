# 用量统计走专用用量日志表

状态：已采纳

背景：会话页要给出「全部对话」的 token 用量（总览 / 按天 / 按模型 / 按会话）。用量只有一处在库里：
`assistant/message` 事件的 `data.usage`（input / output / cacheRead / reasoning / total）。最初直接对
`t_events` 做 SQL 聚合（`json_extract` + 走现成的 `f_role` 索引以避开全表扫描），实测在真实库
（11.9 万行事件、1.99 万条用量）仍需 **1.6s**：瓶颈是逐行解析事件 JSON，而且每次统计都要重付一遍。

**决定**

写路径把用量落进**专用表 `t_event_usage`**（一条 `assistant/message` 事件行 = 一行：事件时间、
provider/model 与五个 token 字段），统计只读这张表；老库在**首次打开时一次性回填**：

- **写路径**：`insertEvents` 顺带解析该事件并插入用量行（`ON CONFLICT DO NOTHING`；fork 复用的事件行不重复记）。
- **回填**：migrate 之后若用量表为空，用一条 `INSERT ... SELECT` 从 `t_events` 补齐——两种 `f_data` 结构都认
  （老行只存 `data`、新行存完整事件），与读路径 `rowToEvent` 的兼容判定一致；幂等，表非空即跳过。
- **统计**：`t_event_usage` + 桥接行 `EXISTS` 判定聚合，不再解析 JSON。
- **口径不变**：只算被会话引用的事件行（fork 共享行计一次、已删会话的孤儿行不计）；`subagent` 按
  「是否被任何 subagent 会话引用」拆分（`human + subagent = totals`）；按会话的行是各会话自己的日志口径
  （fork 子会话含继承前缀，故各行之和 ≥ 总量）。
- **GC 顺带回收**：孤儿事件行被删后，删掉不再有事件行的用量行（外键 `ON DELETE CASCADE` 之外再显式清一次）。

**考虑过的选项**

- **继续直接扫 `t_events`**（走 `f_role` 索引）：1.6s/次，每次都付 JSON 解析成本。
- **只给 `f_type` 加索引**：省掉扫描，省不掉 JSON 解析。
- **按会话维度建汇总表**：fork 派生会复制继承前缀，汇总行也要跟着复制，写路径更重。
- **用 drizzle-kit generate 建迁移**：本仓库的 schema 是运行期动态构造（`toSqliteSchema(tableDefs)`），
  drizzle-kit 静态分析不到表，generate 报「无变化」→ 迁移按现有 journal-less 格式手写
  （migration.sql + snapshot.json 的 id/prevIds 链）。
- **bump `SCHEMA_VERSION`**：不必要——迁移由 `__drizzle_migrations` 记录、与 `PRAGMA user_version` 无关；
  加表是向后兼容的（旧代码既不写也不读它），改版本号反而让现有库被判不兼容。

**后果**

- 统计稳定在 **~140ms**（真实库副本实测：29 个桶、176 条会话行；改造前 ~1.6s），口径与数值不变。
- 首次打开旧库多 **~2.2s**（一次性回填 1.99 万行），此后不再发生。
- `t_event_usage` 是事件行的从属数据：外键级联 + GC 显式清理，不会长期堆积孤儿行。
