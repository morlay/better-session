# 会话删除仅限已归档且硬删

状态：已采纳（实现细节「删除顺带清孤儿」被
[ADR-删除不再清孤儿与vacuum独立成gc通道](20260918-删除不再清孤儿与vacuum独立成gc通道.md) 修订，
三条守卫不变）

上游没有任何会话删除面：`SessionPersistence` 只有 `create` / `open` / `flush`
/ `stat` / `list`，workspace 服务只有 `archiveSession` / `unarchiveSession`，
UI 插槽里也没有会话级位置（0.1.6 相对 0.1.5 只新增
`conversation.input.permission`）。删除因此由本包自持：
`SessionPersistenceRdb.deleteSession(id)` 在**一个事务**内删除桥接行、投影
checkpoint、workspace 归属行与会话行（孤儿事件行的回收见上述修订）。

三条守卫：

- **只删已归档会话**：`t_sessions.f_archived_at` 为空即
  `SESSION_NOT_ARCHIVED`——删除是归档的下一步，未归档会话不提供删除。
- **live 拒绝**：有打开的 handle（读或写）或未 materialize 的 pending 时为
  `SESSION_LIVE`，要求先停止与关闭，避免与写路径并发。
- **删除前取消归档**：经上游 `workspaceRegistry.unarchiveSession` 退场，
  归档集与 feed 增量立即一致（直接改域状态会绕过内存状态）。

client 通道沿用导入端点那条路（`webServer` exact route +
`connection.requestRejection`）：`POST /api/session.delete`，body
`{ sessionId }`；状态映射 404 不存在 / 409 未归档或 live。

## 考虑过的选项

- **软删（tombstone）**：列表、搜索、血缘、归档集与投影层都要感知隐藏标记，
  成本远高于收益；硬删后上游加载期的 headers 扫描天然收敛归属。
- **允许删除未归档会话**：任何会话都可能被误删，也与"归档=待清理"的操作
  习惯冲突。
- **自研 UI 页面（settings.section）**：插槽语义上可行（上游 Archived
  sessions 页正是这么注册的），但当前只需要数据面能力；入口等官方在会话行
  或归档页给出位置再接，不自造抽象。

## 后果

- 删除不可恢复：事件行与投影 checkpoint 一并消失。fork 子会话复用的**共享
  事件行**因仍被引用而保留，孤儿清理只删无人引用的事件。
- workspace 归属 accounting 由上游在加载期按会话 headers 重算收敛；运行期
  侧边栏分组可能短暂保留死 id（点开即 not found）。
- 有 fork 子会话的父会话可删除，子会话血缘引用悬空但仍可打开；"先删子会话"
  的严格模式留给后续按需加。
