# 删除不再清孤儿，孤儿回收与 VACUUM 独立成 GC 通道

状态：已采纳

背景：[ADR-会话删除仅限已归档且硬删](20260917-会话删除仅限已归档且硬删.md) 把「删除该会话的行」
和「全库孤儿事件行清理」放进同一个事务。实测（503MB 库、11.9 万 `t_events` 行、被删会话 1 万行事件）：
只删该会话的 4 张表 **545ms**，那句
`DELETE FROM t_events WHERE f_event_id NOT IN (SELECT … FROM t_session_events)` **1717ms**——
每次删除都在为全库做一次孤儿扫描与删除，删掉的会话立刻不留孤儿，历史孤儿却无人回收，也没有
VACUUM，库文件只增不减。

**决定**

删除只落该会话的行（桥接行、workspace 归属行、投影 checkpoint、会话行），不再碰 `t_events`；
**两类孤儿**的回收与 VACUUM 独立成 `POST /api/session.gc`——先让所有运行中的 agent 退场，再回收
「父已不存在的 subagent 会话」（`origin = 'subagent'` 且父不在表里，live 的跳过），随后回收无桥接行
引用的事件行，最后 VACUUM，一次请求回报 `{ orphanSessions, orphanEvents, stoppedAgents, vacuumed }`。
导出另开一条通道 `POST /api/session.export`，直接把会话日志打成 zip 响应体（与导入通道读同一份 artifact）。

**考虑过的选项**

- 保留每次删除清孤儿、只优化 SQL：孤儿判定必须全库范围（fork 子会话共享事件行），单条删除注定为全库付费。
- 删除时只清本次会话独占的事件行：库不膨胀，但每次删除多一轮独占判定（1 万次索引查询），且与 GC 入口重复。
- 删父会话时级联删它的 subagent 子会话：删除会变成无法预估的大事务（一个父可能挂着上百个子会话），
  与「删除是轻操作」冲突；父还在的 subagent 会话也不该被顺带清掉。
- GC 由后台定时触发：用户看不到也停不下 agent，删除与运行中的写路径可能撞车。
- 导出复用导入的 base64 JSON 通道：大会话多占 33% 内存与体积，浏览器还要多解一次码。

**后果**

- 删除回到「查不到就好」，成本与该会话大小线性（1 万行 ≈ 0.5s）。三条守卫不变：只删已归档、
  live 拒绝、删前经 `workspaceRegistry.unarchiveSession` 退场。
- 删掉的会话会在 `t_events` 留下孤儿行，**库体积不随删除下降**，直到执行 GC。
- 孤儿有两类、在同一次 GC 里清：父被删后留下的 subagent 会话（连带其桥接行、workspace 归属行、
  投影行，独占的事件行随后按「无引用」回收），以及已无桥接行引用的事件行。父仍在的 subagent 会话不动
  ——它仍是父的执行记录。
- GC 会停止所有运行中的 agent（`ctx.agents.list()` 逐个 cancel 并等 `whenIdle`），VACUUM 期间不得有
  并发写；入口由「对话管理」页以一个不可关闭的等待弹窗阻塞操作，避免用户在此期间做别的。
- Postgres 侧同样两步拆开：`collectOrphanSessions` / `collectOrphans` 走普通删除，`vacuum` 用
  `VACUUM ANALYZE`（不得在事务内执行）。
