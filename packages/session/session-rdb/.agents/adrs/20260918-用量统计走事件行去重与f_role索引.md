# 用量统计走事件行去重与 f_role 索引

状态：已采纳

背景：会话页要给出「全部对话」的 token 用量（总览 / 按天 / 按模型 / 按会话）。用量只有一处在库里：
`assistant/message` 事件的 `data.usage`（input / output / cacheRead / reasoning / total）。
`t_events` 上没有 `f_type` 索引，按 `f_type='assistant/message'` 过滤是全表扫描（实测：11.9 万行、
1.99 万条用量事件 → **1.6s**）；而 `f_role='assistant'` 有索引，且实测与该类型**完全等价**（同为 19,905 行）。

**决定**

统计由 host 侧 SQL 聚合（`POST /api/session.usage` 一次回报 总览 + 桶 + 会话行），口径三条：

- **只算被会话引用的事件行**：`EXISTS` 桥接行过滤。fork 共享行因此只计一次，已删会话留下的孤儿行不计。
- **走 `f_role='assistant'` 索引**：与 `f_type='assistant/message'` 等价，实测 1.6s → 0.42s；不改 schema、不加迁移。
- **两种 `f_data` 结构都认**：老行只存 `data`、新行存完整事件（见
  [ADR-事件实体全局化](20260917-事件实体全局化与桥接行承载会话专属信息.md)），聚合用
  `coalesce(json_extract(f_data,'$.data.usage.x'), json_extract(f_data,'$.usage.x'))`——与读路径
  `rowToEvent` 的兼容判定一致。库里两种结构并存时（本机：19,753 带信封 + 174 老行）都得计入。

**考虑过的选项**

- **加 `f_type` 索引**：能提速，但要动 schema 与迁移，而现成的 `f_role` 索引已经够。
- **写路径维护用量汇总表**：统计变快，但每条事件都要写汇总，重路径变重且要处理历史回填。
- **客户端聚合**：只能覆盖已加载的会话与投影，拿不到全库（含已归档、以及删除前的用量）。
- **只认新结构**：实现最简单，但 174 行老数据静默漏计。

**后果**

- 一次全库聚合约 1~2 秒（`coalesce` 双路径让每行多解析一次 JSON）；页面只在进入统计视图时请求一次，
  维度切换在本地折叠。
- `subagent` 按「该事件行是否被任何 subagent 会话引用」拆分：`human + subagent = totals`，不重复计。
- 按会话的行是**各会话自己的日志口径**（fork 子会话含继承前缀），因此各行之和 ≥ 总量。
