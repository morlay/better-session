# 自研离线桌面打包器，而非直接用上游桌面应用

状态：已采纳（当前形态：共享 Web profile + `dsh-app://` 认证反向代理 + IPC boot，协议 4）

## 背景

诉求是把**任意工作区**打包成**离线可安装**的桌面应用——产物在目标机器上不再联网、不再拉依赖就能跑——而且工具本身**可发布**（作为 `@morlay/*` 包对外安装，仓库内外的任意工作区都能用）。

## 为什么不能直接用上游

1. **上游 `apps/desktop` 是官方发布态应用，不是「给任意工作区打包」的工具。** `vendor/deepseek-harness/apps/desktop` 的 app 身份（`@deepseek-ai/dsh-desktop`）、窗口与菜单、更新器（`installDesktopUpdateTaskControl` / `update-tasks`）、签名与打包流程（`electron-builder.config.mjs` + `installer/`）都绑在它自己的发行物上。
2. **上游 host 是 private 包，外部装不到。** `vendor/deepseek-harness/apps/desktop-host/package.json` 的 `@deepseek-ai/dsh-desktop-host` 是 `private: true`、不发布，所以变体做成了**我们自己的包** `@morlay/dsh-desktop-host`（上游入口逐行复制 + 两处本地适配，产物 `lib/index.js`，manifest 只声明这份代码真正用到的依赖），由打包工具 `@morlay/dsh-desktopify` 依赖并复制进部署——载荷的身份、入口与依赖清单都归这个包，工具只负责装配。
3. **上游桌面与 Web 共用一套 profile，壳不需要另写后端启动逻辑。** `vendor/deepseek-harness/apps/desktop-host/src/index.ts` 用 `runProfile({ profile: 'desktop', patchFiles: [] })`，由 runner 自己组合 `dsh-base` + `dsh-web-app`。壳只做三件事——提供本地 dist、认证反向代理、IPC boot——**自研的增量只剩壳这一层**。

## 考虑过的选项

- **直接用上游 Electron 应用**：承载不了任意工作区自己的 app 身份与打包流程，且它的 host 是 private 包（理由见上 1、2）。
- **为桌面另写宿主与启动逻辑**：多出第二套后端启动路径，与上游分叉，升级时双份维护，还要额外一套 golang 工具链。
- **复用上游 host 的纯 node 实现 + 自研壳**：采纳。

## 决定

- **工具形态**：bin `dsh-desktopify`，`dev` / `bundle` 两个子命令，工作区作为参数（缺省当前目录）；工具内不写死 app 路径或名字。
- **复用上游 host 产物与协议**：自带 desktop-host 构建产物，按它的 IPC 协议装配，不重复实现 boot。
- **离线打包链路**：`pnpm deploy --prod` 导出依赖闭包 → 种子 → 随包 Node → electron-builder `--dir`；无签名、无 notarize、无开发者账号。
- **官方依赖由工具内部维护**：`@deepseek-ai/*` 清单、依赖 spec 解析与 bundle 合并都在工具里；app 只声明自己的依赖与 bundles。

## 影响

- 工具可独立发布：不依赖上游 private 包，仓库外的工作区也能装。
- 与上游共享 host 协议与后端：升级只需跟随 vendor 版本。
- 上游桌面与 web 共用一套 profile（`dsh-base` + `dsh-web-app`），壳不维护桌面专属 patch。
- 离线产物无签名，是自用定位（不追求分发合规）。
