# 改进（improve）

发现架构摩擦，提出**深化机会**——把浅层模块变成深层模块。目标是可测试性与可导航性。
产出是候选清单与决策，不是代码；**一次只推进一个候选**。

## 一、词汇与既有决策

- 架构词汇与判据来自 [`dsh-plugin-design`](../dsh-plugin-design/SKILL.md)：模块、接口、实现、深度、浅层、
  接缝、适配器、杠杆效应、局部性；以及删除测试、「接口就是测试面」、「一个适配器 = 假想接缝，两个 = 真接缝」。
  用这些词，不要漂到「组件」「服务」「边界」。
- 领域名用 `.agents/CONTEXT.md` 里的词（边界见 [`.agents/CONTEXT-MAP.md`](../../CONTEXT-MAP.md)）；上游名一律
  用上游真源目录里的词。
- 既有决策不重新讨论，已立的债不重复立项：见各层的 `.agents/adrs/` 与 `.agents/debts/`。

## 二、定范围（YAGNI 优先）

深化的收益是「以后改它更容易」，所以把权重压在**最近在改的地方**：

- 用户指了方向（包 / 上下文 / 子系统 / 痛点）→ 用它，跳过推断；
- 否则用近期提交找热点（`git log --oneline -40`），看 `packages/<family>/<pkg>/` 下哪些路径反复出现；
- 变更分散、没有热点 → 扩大范围，但报告里要写明为什么。

## 三、扫描

先读涉及上下文的 `.agents/CONTEXT.md` 与 ADR，再派子代理遍历代码，只记**确实遇到摩擦**的地方：

- 理解一个概念要在许多小包之间跳（同一 family 下多包区尤其容易）？
- 哪里**浅层**——插件只是薄薄包一层上游服务再注册，接口几乎和实现一样复杂？
- 哪里纯函数只为可测试性被抽出来，真正的缺陷藏在调用方式里（没有**局部性**）？
- 哪里紧耦合的包跨接缝泄漏（上游私有字段名、字符串标识漏进消费侧）？
- 哪里没有测试，或难以从当前接口测试（对应改动所属层 standards 里「已知未覆盖」的位置是否该还了）？
- 重复：整包 fork / 复制段与上游、或与我们自己其余包之间的重叠形态（差异与回退条件登记在该层
  `.agents/debts/`）。

对可疑项做**删除测试**：删掉它，复杂度集中了（信号），还是只是搬了个地方？

## 四、出报告

写到仓库约定的临时产物目录 `.scratch/`（`.gitignore` 里忽略，不进仓库），文件名带时间戳，把绝对路径告诉
用户。**不输出 HTML**；格式见 [`references/report-format.md`](./references/report-format.md)。

- **与既有 ADR 冲突**：只有摩擦大到值得重开那条 ADR 才提，并在卡片里标注（「与 `ADR-<YYYYMMDD>-<slug>`
  矛盾，但值得重开因为…」）；不要罗列 ADR 禁止的理论重构。
- 用户选中之前**不要**提接口——方案只写方向。

## 五、把选定项落回流程

选定后按 [`dsh-plugin-design`](../dsh-plugin-design/SKILL.md) 的判据与模板落记录，再进实现——它决定每类产出
（设计、ADR、债务、术语）写进哪个 home；本技能不另立一套判据。落地走 `dsh-plugin-implement`，改完审查走
`dsh-plugin-review`；触及上游只读面走 `dsh-plugin-upstream-sync`。

收尾：只做选定的那一个，其余候选留在报告里；不要顺手把整份报告都改了。
